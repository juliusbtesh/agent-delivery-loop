# Delivery Loop

Coordinate the existing `delivery-backlog`, `delivery-implement`, and `delivery-audit` skills. The coordinator owns task selection, handoffs, stopping conditions, and final status; it does not substitute its own verdict for the audit.

## Configure

Use the task slug or ordered task list the user selected. Preserve that order. Distinguish an ordered chain from a code dependency: the next task branches from the previous feature only when its implementation actually needs that unmerged work. Determine this from the task source and current code, or ask when ambiguous; otherwise branch it from the project's integration branch. If they authorize processing the backlog generally, select only ready tasks whose prerequisites are met; do not treat discovery suggestions as approved tasks. Accept an implementation model and audit model when the user specifies them. Check available models and pass supported choices to the agent launcher; otherwise use its defaults. Do not claim a model was used unless the launcher confirms it. Use separate implementation and audit agents with access to the same task worktree and dispatch files. If the environment cannot launch or await independent agents, explain that the automated loop is unavailable and leave a clear handoff for manual execution.

The coordinator owns the dispatch as well as the handoffs. When the user decides something during a run, write the decision into the affected dispatch, dated, before telling the agent; a decision that lives only in a message is lost to the next agent and to the audit. When an implementer or auditor reports that the dispatch itself is wrong (it contradicts the code or a repository rule, or rests on something false), correct the dispatch and say what changed; do not relay a workaround. When a task turns out to need a change outside its own repository or scope, such as a fix in a shared library, stop that task and tell the user: the outside change is its own piece of work with its own approval, and the task resumes once it exists.

Default to at most two remediation rounds per task unless the user sets another limit. A tool failure, missing access, material scope change, or unresolved audit finding at the limit stops that task and returns it to the user. Never convert a failed or unverified audit into acceptance to keep the queue moving.

## Run one task

1. Use an existing current dispatch for the selected task, or have `delivery-backlog` prepare one on a task-specific feature branch. Do not overwrite an active round merely to restart the loop. Confirm the integration branch, parent branch, exact base commit, feature branch, worktree, prerequisites, and acceptance checks. For an older in-progress dispatch missing branch fields, reconcile its actual checkout and baseline before continuing; do not silently transplant the work. Give all agents that worktree path. Every task runs in its own new worktree on its own feature branch; never in the main checkout. The integration branch is the one the project's workflow names; when it names none, `delivery-backlog` uses `development` if that branch exists and asks otherwise. Keep implementation and audit sequential on the same task; do not dispatch another task in that worktree while one is awaiting audit.
2. Send the dispatch slug and path to a fresh implementation agent with `delivery-implement`, the chosen model if supported, and the instruction to write its summary. Await completion and check that the expected summary and worktree changes exist. A missing or failed handoff stops the round; report the problem rather than sending an empty audit.
3. Send the same slug to a separate audit agent with `delivery-audit` and the chosen model if supported. Await its verdict and inspect the written dispatch/status so the callback matches the current round.
4. On **remediation needed**, send the updated round back to the same implementation agent when available, preserving the existing work and context. Await its new summary, then ask the independent audit agent to check that round. Repeat until accepted or the configured round limit is reached. If the audit says **cannot verify**, stop for the named prerequisite; do not retry blindly.
5. On **accepted**, verify that the audit applies to the latest implementation round and that no new task-owned changes appeared afterward. Confirm that `delivery-audit` completed its accepted-task closure: the existing task source is done or accepted and, by default, a detailed local commit contains only the task-owned changes on the recorded feature branch. Honor an explicit no-commit instruction and verify the recorded opt-out instead. If commit or status closure failed, stop the queue and report **accepted but closure blocked**; do not mark the task complete or create a duplicate commit. Report the verdict, checks, limitations, task status, branch, and commit SHA when present. A local commit does not authorize a merge, push, release, or deployment.

For an approved queue, move to the next task only after closing the current one. Re-read the task source and repository state, confirm its prerequisites, and choose its branch base: the accepted feature tip for a dependent task whose prerequisite remains unmerged, or the integration branch tip for an independent task. Do not assume the prior feature has reached the integration branch merely because it was committed. Prepare the next dispatch in its own feature branch from the chosen base, then launch a new implementation agent and repeat the independent audit loop. If a prerequisite has no accepted commit because committing was opted out, stop and ask how to establish a reliable branch base. Stop the queue on a blocked task unless the user explicitly authorized skipping blocked items. Keep the user informed at meaningful boundaries without treating silence as approval for new scope.

After the queue ends or stops, give one consolidated report in task order: outcome and audit verdict for each task, remediation rounds, checks run and material limits, task status, feature branch and parent branch, commit SHA or recorded no-commit choice, and any unfinished tasks with their exact blocker. For every accepted task say how far it has travelled: committed on its feature branch, integrated, or (where the project has a promotion chain) promoted and to which branch. State which branches are still unmerged. Distinguish completed work from work that only passed audit but could not be closed. Do not repeat the full implementation summaries in the final report.

## Tasks that meet at a contract

When a run includes tasks in more than one repository that depend on each other, or a task changes something another repository in the run consumes, write the shared contract into every affected dispatch before any implementation starts, word for word the same: the route or message, the request and response shapes, the status codes, and who may call it. Each task is still audited on its own. Auditing each side against its own dispatch does not show that the two sides agree, so once both are accepted, have an audit agent run the contract-drift lens of `delivery-audit` across both task worktrees, comparing what one side really sends and reads with what the other really serves. Do not report the run as complete until that comparison has passed. A mismatch goes back to the task whose code departs from the agreed contract as a remediation round; if the contract itself was wrong, correct it in every dispatch and say so.

## After the run

A run is not finished when its tasks are accepted. Accepted work sits on feature branches until it is integrated, and integrated work sits on the integration branch until it is promoted. Carry the run through the steps below in order, stopping for the user where stated, so that the tail of the process is not left to be worked out by hand.

### Integrate

Integration is merging accepted task branches into the integration branch. Acceptance never implies it: when the queue has ended, show the user what would be merged and ask for a go-ahead for those branches.

- Only a task that is accepted and committed can be integrated. A task accepted without a commit, because the project or the user opted out, cannot: report that it needs the owner's commit first and leave it where it is.
- Finish any contract comparison between repositories before integrating either side.
- Merge in dependency order. A branch cut from another task's tip already contains that task; merge the earlier task first so that each one arrives as its own merge, or merge only the last tip and say that it carries the earlier ones.
- Use the method the project's workflow records. Where it is a pull request: push the feature branch, open the pull request into the integration branch, wait for the required checks, and merge when they pass. Never bypass a required check or a branch rule, even from an account that is allowed to. Where it is a local merge: build the merge in a temporary worktree at the integration branch's current tip, not in the main checkout, with a merge commit and no squash or rebase.
- The integration branch has usually moved since the task was dispatched, so the merged result is something no audit has seen. Run the project's checks on it. If files the task changed were also changed on the integration branch since the task's `Base`, have an audit agent review that overlap even when the merge is clean and the checks pass.
- Do not resolve a conflict or a failing check by guessing. Two tasks that each updated their own line of the task source may both be kept. Anything else goes back to the task as a remediation round: bring the integration branch into the feature branch in that task's worktree, fix it there, and audit the difference before trying again.
- Move the integration branch only by fast-forward to the merge you verified. When that branch is checked out in the main checkout, fast-forward it there, and only if that checkout has no uncommitted work; say beforehand that it will move. If it has uncommitted work, stop and ask. Never move a branch that is checked out somewhere from outside that checkout: its files and index would no longer match it.
- Pushing the integration branch to a remote needs its own authorization unless the go-ahead named it.

Report the merge commits, the checks run on the merged result, and anything that was not integrated and why.

### Clean up

A task's worktree and feature branch outlive acceptance only until the work is merged. Once the user has had a feature branch merged into the integration branch (a separate, authorized action), remove that task's worktree with `git worktree remove` and delete its local feature branch, after checking that the worktree has no uncommitted or untracked task work and that the branch is fully contained in the integration branch. Never remove a worktree for a task that is unmerged, awaiting audit, blocked, or accepted without a commit; those are the only copy of the work. A worktree is a directory like any other: if it contains a link to a folder outside itself (for example a linked dependency folder), remove the link itself first so the target is not deleted with it. In the consolidated report, list every worktree and branch this run created and say which still exist and why.

### Hand off to promotion

When the project's workflow records a promotion chain, end the report by saying what is now integrated but not yet promoted, using the report mode of `delivery-promote`, and that promotion is the next step and who carries it out according to the workflow. Do not promote as part of a run: each promotion step needs its own go-ahead, and finishing a set of tasks must not carry work toward production by momentum. When the project records no chain, say nothing about promotion.
