# Delivery Setup

Set up the delivery loop for the repository the user names, or the current repository if none is named. The reusable delivery skills describe the protocol; the project owns its task source, checks, invariants, and release rules. Do not copy another project's choices into this one.

First determine whether the target is an established project, a partly initialized project, or an empty folder. A folder is not empty merely because it has no commits: inspect hidden files and untracked content as well. Apply the existing-project discovery below to any material files already present; use the fresh-project path only when there are no project decisions to preserve. If the folder is not a Git repository, do not require Git history to begin setup.

## Discover

Inventory existing agent configuration before proposing a new one. Search the root and affected subtrees for `AGENTS.md`, `CLAUDE.md`, `AGENT_WORKFLOW.md`, project skills (`SKILL.md` under agent-specific skill directories), agent commands or rules, and any workflow documents they reference. Include hidden files and follow relevant skill symlinks; inspect file contents, not just names. Also inspect the task tracker, manifests and scripts, CI, tests, architecture or product documentation, and Git status when Git is initialized. Keep the search bounded to relevant project files; do not read secret values or copy credentials into generated files.

Compare existing instructions with the proposed delivery loop by topic: task source, command names and routing, handoff paths, integration and feature branch conventions, checks, product invariants, task status, and commit or release policy. Record the source and scope of each rule. Merge compatible information by referencing its existing source or incorporating it into the canonical workflow where appropriate. Do not replace an existing command or skill, create a second task source, or write a rule that contradicts an active instruction merely to fit this skill set.

Ask the user about material conflicts that the repository does not resolve, naming the conflicting files and the effect of each choice. Also ask about decisions that affect the workflow and cannot be established from the repository: for example, which of two live task sources is authoritative, which checks are mandatory, or a product rule not recorded elsewhere. Present the evidence and a reasonable default when one exists. Continue independent setup work while awaiting an answer, but do not write the disputed rule or overwrite the conflicting file. Do not invent product invariants or claim a command is required merely because it exists.

## Fresh project

For an empty folder, ask what the user wants to create and what the first useful outcome should be. Resolve only the choices needed to start a real backlog: intended users and core behavior, immediate scope and boundaries, any chosen stack or constraints, and the first concrete tasks or milestones. Ask in a compact round and use answers already supplied in the conversation; do not make the user restate them. Suggest a small ordered set of specific tasks with observable completion criteria and prerequisites, then let the user correct material assumptions. Avoid turning vague ideas into invented product requirements.

Once there is enough direction, create `BACKLOG.md` with stable slugs and actionable first tasks, ordered so prerequisites precede dependent work. Put known product decisions and any verified checks in `AGENT_WORKFLOW.md`; mark unchosen stack, commands, and project-specific policies as pending instead of pretending they exist. Record the delivery loop's default of a detailed local commit after accepted audit, unless the user chooses otherwise. Create the local workflow skill and ignore rule as below. If the user has not yet defined what to build, leave the project-specific backlog pending and ask for that missing direction. Setup does not scaffold the application, dispatch a task, initialize Git, or make a commit unless requested. Tell the user that the first dispatch needs a Git repository with an initial commit so feature branches and worktrees have a reliable base; setup and backlog editing can happen before Git initialization.

## Create or refresh

1. Write or update root `AGENT_WORKFLOW.md` as the canonical project configuration. Keep it short and specific: task source and stable task IDs, integration branch and any feature branch naming convention, relevant verification commands and when to run them, product or data invariants, release/commit policy, and the `.agent-delivery/dispatch/` handoff location. State that accepted tasks receive a detailed local commit by default and pushes are separate, unless the user or existing project rules choose otherwise. Record the project's branch model: the integration branch that task branches are cut from and merged into, and the promotion chain after it (of any length: for example integration then production; integration, staging, production; or several staging branches before production). Settle it with the user once instead of assuming it. For an existing project, read the branches that exist and how they are used, propose the model that matches, and ask the user to confirm; record a branch other than `development` as the integration branch only when the project already works that way. For a fresh project, ask how many stages the work passes through before it reaches users, since projects differ: integration and production only, integration and a single staging branch, the common three, or several intermediate stages. Suggest `development` as the integration branch with `staging` and `production` after it as a starting point, not a requirement, and record the chain the user chooses with the names they choose. Offer to create the branches that are missing; create them locally only when the user agrees, and never push them as part of setup. Do not assume `main`. State that the delivery loop only ever branches from and merges into the integration branch and never touches the promotion branches. When the project has a promotion chain, also record how promotion works there, because it differs between projects and `delivery-promote` follows what is written: which steps an agent may carry out and which belong to the owner or a release pipeline, whether a step is a pull request or a merge and push, what must be true before a step (required checks, approvals, a version bump), and any other repository that must be released before or after this one. Ask; do not assume. A project with no chain records that promotion does not apply. State that every task is dispatched into its own new worktree on its own feature branch, never the main checkout; name where those worktrees go; and state that a task's worktree and branch are removed once its work is merged. Reference existing instructions instead of duplicating them. Mark unresolved items explicitly; do not replace them with guessed rules.
2. Create or update one thin project-local `project-delivery` skill, normally at `skills/project-delivery/SKILL.md`. Its `SKILL.md` must point to root `AGENT_WORKFLOW.md`, explain when to consult it, and route setup, task discovery, backlog, implementation, audit, and coordinated loop requests to `delivery-setup`, `delivery-discover`, `delivery-backlog`, `delivery-implement`, `delivery-audit`, and `delivery-loop`, and promotion requests to `delivery-promote` when the workflow records a promotion chain. Keep project-specific values in `AGENT_WORKFLOW.md`, not a second copy inside the skill. Reuse an existing equivalent skill when possible; avoid a duplicate entry point. Make relative directory symlinks from `.agents/skills/project-delivery` (Codex) and `.claude/skills/project-delivery` (Claude Code) to that canonical skill. On Windows without the right to create symbolic links, do not substitute a directory junction here: a junction stores an absolute path and would break in other clones and worktrees. Leave the two links uncreated, record that in `AGENT_WORKFLOW.md`, and give the user the canonical path; the seven personal skills still work without them. If an existing path is a file, directory, or symlink, inspect and reconcile it before changing it; never overwrite a different skill. Keep the canonical skill and its relative links in the project so they work in other clones and worktrees. For another agent, use its documented project skill directory when available, or give the user the canonical path to load explicitly. Do not claim that one discovery directory serves every agent.
3. Check whether all seven reusable `delivery-*` skills are discoverable by each agent the project uses. The project-local skill is a router, not a copy of those seven skills. For local Codex and Claude Code, run this skill set's `scripts/install.py` from its checkout to report missing and conflicting personal links; `--install` creates missing links without replacing existing entries. Use it when the checkout is available and local setup is authorized. Inspect and reconcile conflicts before changing them. Otherwise give the user exact install steps and mark that agent's setup incomplete. Do not commit absolute links to an external checkout into an adopting project: they break on another machine. If the user needs a self-contained repository or cloud session, arrange a project-contained copy or dependency first, then link relatively from each agent directory.
4. Add `.agent-delivery/dispatch/` to the project's `.gitignore` if it is not already ignored. Preserve existing ignore rules. Do not create a new backlog when the project already uses another task source. For a fresh project, seed `BACKLOG.md` with the agreed initial tasks rather than an empty placeholder.

Preserve existing workflow files and user edits; update in place after reconciling differences. Repository instructions and the user's current request take precedence over the generated workflow. Setup itself does not commit, push, publish, or deploy; its accepted-task commit default applies only after a later successful audit. A push, publication, or deployment always needs separate authorization.

## Verify and hand off

Recheck the effective instructions and skill entry points for contradictory task sources, command routing, checks, or release rules. Check that every recorded path and command exists or is clearly marked as pending, the local skill has valid frontmatter and points to the canonical workflow, both project skill links resolve to that same file, and handoff files are ignored. Verify discovery of each reusable skill in the selected agents' skill locations; report missing skills or unsupported agents plainly. For a fresh project, check that backlog tasks describe observable outcomes, have unique slugs, and respect prerequisites. Summarize the existing files examined or fresh-project decisions gathered, how compatible rules were merged, any conflict and its resolution or pending question, files changed, and the invocation path for each selected agent. A successful setup leaves `delivery-backlog` ready to read the real task source; it does not dispatch or implement a task unless asked.
